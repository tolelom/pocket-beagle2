# 02. 부팅은 어떻게 일어나는가

> 전원을 넣은 순간부터 리눅스 로그인 화면까지 무슨 일이 벌어지는지 따라간다. 그리고 그중 어디까지가 우리가 바꿀 수 있는 영역인지 본다.

## 2-1. 왜 단계가 여럿인가

부팅이 한 방에 끝나지 않는 이유는 닭과 달걀 문제 때문이다.

리눅스를 올리려면 DRAM이 필요하다. 리눅스 커널만 해도 수십 MB이고, 칩 안에 그만한
메모리는 없다. 그런데 DRAM은 그냥 꽂혀 있다고 쓸 수 있는 게 아니다. 메모리 컨트롤러를
초기화하고, 타이밍 파라미터를 넣고, 캘리브레이션을 돌려야 한다. 그 초기화 코드도
어딘가에서 실행되어야 하는데, 아직 DRAM이 없으니 DRAM에 둘 수는 없다.

해결책은 칩 안에 있는 작은 SRAM을 쓰는 것이다. 수백 KB 정도라 리눅스는 어림도 없지만
DRAM 초기화 코드 정도는 들어간다. 그래서 순서가 이렇게 된다.

1. ROM이 작은 프로그램을 SRAM에 올린다
2. 그 프로그램이 DRAM을 켠다
3. 이제 DRAM에 큰 프로그램을 읽어 들인다
4. 큰 프로그램이 리눅스를 올린다

여기에 보안 검사와 코어 전환이 얹히면서 실제 단계는 더 늘어난다.

## 2-2. 전체 흐름

왼쪽 세로줄을 따라 시간이 흐르고, 각 칸의 앞머리가 그 일을 하는 주체다. 주체가 바뀌는
지점마다 실행되는 코드도 다른 파일에서 온다.

대괄호로 적은 것은 실제 콘솔에 찍히는 문구다. 부팅 로그를 볼 때 지금 어느 단계인지
가늠하는 표지로 쓸 수 있다.

```
전원 램프업
  |
  +- SMS M4F(TIFS): RTI 워치독 180초 설정
  |                 PLLCTRL 설정, MCU PLL 락
  |                 부트 모드별 기본 방화벽 설정
  |                 Secure Proxy / Ring Accelerator 설정
  |                 R5에게 부트 모드 정보 전달
  |                 R5 CPU0 리셋 해제
  |
  +- R5 Public ROM: BOOTMODE 스트랩 확인 후 부팅 장치 초기화
  |                 이미지 수신, 형식 1차 검사, M4로 전달
  |
  +- SMS M4F(TIFS): X.509 파싱, SA2UL SHA512로 무결성 검증
  |                 통과 시 R5 리셋 → 부트벡터를 새 이미지로 → 리셋 해제
  |                 (Public ROM은 완전히 분리된다)
  |
  +- R5: tiboot3.bin의 SPL 실행                 [SPL 배너 1회차]
  |      DDR 초기화, tispl.bin 로드              [Authentication passed x5]
  |
  +- A53: TF-A BL31 v2.14.1 (EL3)
  |       OP-TEE 4.9.0 (S-EL1), 초기화 후 콘솔 닫음
  |       A53 SPL                               [SPL 배너 2회차]
  |       u-boot.img 로드                        [Authentication passed x2]
  |
  +- U-Boot 2026.01: extlinux.conf 해석
  |
  +- 리눅스 → 데비안
```

## 2-3. 그림에서 눈여겨볼 점

**같은 R5 코어가 두 번 등장한다.** 처음에는 칩에 구워진 ROM 코드로 시작하고, 그다음
리셋된 뒤 우리가 만든 SPL로 다시 시작한다. ROM이 이미지를 받아 검증까지 마치면, 그 ROM
자체를 완전히 분리한 상태에서 새 코드를 실행한다.

**TI 펌웨어가 중간에 다시 끼어든다.** ROM이 이미지를 받기는 하지만 서명 검증은 직접
하지 않는다. SMS의 M4F에 넘겨서 검사시키고 결과만 받는다. 암호 연산과 열쇠를 한 코어에
가두는 구조다.

**A53은 한참 뒤에야 켜진다.** 리눅스가 도는 메인 코어인데도 부팅 중반까지 전원이 들어
있지 않다. R5 SPL이 DDR을 세우고 `tispl.bin`을 올린 뒤에야 깨어난다.

## 2-4. 로그에서 자주 보는 것들

부팅 로그를 처음 보면 같은 것이 여러 번 찍혀서 헷갈린다. 이유가 있다.

`Authentication passed`가 부팅당 7회 찍히는 것은 검증이 파일 단위가 아니라 조각 단위로
일어나기 때문이다. `tispl.bin`의 조각 5개와 `u-boot.img`의 조각 2개를 각각 검증한다.

SPL 배너가 2회 찍히는 것은 SPL이 두 개이기 때문이다. R5용과 A53용을 별도 설정으로 따로
빌드한다. 같은 바이너리가 두 번 도는 게 아니다. 스택 사용량이 13416바이트와
2048바이트로 다르게 찍히는 것으로도 구분된다.

## 2-5. 첫 단계는 온칩 SRAM에 들어가야 한다

ROM이 이미지를 적재하는 시점에 DDR이 아직 초기화되지 않았다. U-Boot가 SPL과 본체로
나뉘어 있고 SPL의 첫 임무 중 하나가 DDR 초기화인 이유가 이것이다.

이 제약이 SPL의 성격을 거의 다 결정한다. 쓸 수 있는 메모리가 수백 KB뿐이라 기능을
넣을 때마다 크기를 걱정해야 하고, 그래서 같은 SPL이라도 용도별로 다르게 빌드한다.
예를 들어 SD 카드로 부팅하는 빌드와 USB로 부팅하는 빌드가 따로 있는데, 둘을 한
바이너리에 넣으면 SRAM에 안 들어가기 때문이다.

### ROM이 이미지를 받는 세 경로

| 경로 | 해당 부트 모드 | 방식 |
|---|---|---|
| Memory | OSPI, QSPI, xSPI, GPMC NOR | 주소 공간에 그대로 보이므로 복사 |
| Block | I2C, USB DFU, UART, eMMC, Ethernet, SD raw | 블록 단위 수신 후 X.509 헤더가 차면 M4로 전달 |
| Filesystem | SD FAT, eMMC FAT | FAT를 읽어 `tiboot3.bin` 파일을 찾음 |

## 2-6. 부팅 장치는 어떻게 정해지나

판정은 ROM이 하고, 무엇을 시도할지는 보드의 저항이 정한다.

전원이 들어올 때 특정 핀들의 전압 상태를 하드웨어가 붙잡아 레지스터에 넣는다. 이렇게
저항으로 고정해둔 설정을 스트랩(strap)이라고 부른다. 소프트웨어로 바꿀 수 없고 보드를
고쳐야 바뀐다.

```
BOOTMODE[15:0] 핀 (풀업·풀다운 저항, USER 버튼)
      | MCU_PORz 해제 시 하드웨어가 래치
      v
CTRLMMR_MAIN_DEVSTAT   0x43000030  (WKUP_CTRL_MMR0_BASE 0x43000000 + 0x30)
      [2:0]   시스템 클럭 주파수 (PLL 설정용)
      [6:3]   primary 부트 모드
      [9:7]   primary 부가 설정
      [12:10] backup 부트 모드
      [13]    backup 부가 설정
      [15:14] 예약
      |
      v
ROM: primary 시도 → 실패 시 backup 시도
     선택 결과를 OCRAM 0x7000F290에 기록
      |
      v
SPL의 get_boot_device(): DEVSTAT와 OCRAM 값을 읽어 해석만 한다
```

여기서 중요한 것은 마지막 줄이다. SPL은 부팅 장치를 고르지 않는다. ROM이 이미 정해서
메모리에 적어둔 값을 읽어 해석할 뿐이다. 그래서 SPL 코드를 아무리 고쳐도 부팅 장치
자체는 바뀌지 않는다.

`0x7000F290`은 U-Boot 헤더의 `K3_BOOT_PARAM_TABLE_INDEX_OCRAM` 값이고 SPL이 실제로 읽는
주소다. TRM Table 5-65는 같은 항목을 `0x43c3f290`으로 적어 두 출처가 갈린다. 어느 쪽을
ROM이 쓰는지는 확정되지 않았다.

### 인코딩

primary(4비트)와 backup(3비트)이 서로 다른 번호 체계를 쓴다. 같은 장치라도 번호가
다르다는 뜻이라 표를 읽을 때 주의해야 한다. backup 필드는 3비트라 0에서 7까지만
표현된다.

```
primary                        backup
0x01 OSPI                      0x01 DFU
0x02 QSPI                      0x03 UART
0x03 SPI                       0x04 Ethernet
0x04 Ethernet RGMII            0x05 MMC
0x05 Ethernet RMII             0x06 SPI
0x06 I2C                       0x07 I2C
0x07 UART
0x08 MMCSD (SD 카드 또는 eMMC UDA)
0x09 eMMC (boot 파티션)
0x0A USB (설정 비트로 DFU 장치 모드와 USB 호스트 MSC 모드를 구분)
0x0B GPMC NAND
0x0C GPMC NOR
0x0E xSPI
0x0F NOBOOT
```

부가 설정 필드가 세부를 정한다. MMCSD는 포트(MMC1·MMC2)와 파일시스템·RAW 여부를,
USB는 DFU 장치 모드인지 호스트 MSC 모드인지를 고른다.

### 이 보드에서 쓸 수 있는 것

| 방법 | 조건 | 프로토콜 |
|---|---|---|
| microSD | 카드 삽입 | primary |
| USB DFU | SD 없음 | backup |
| UART | SD 없음 + USER 버튼을 누른 채 전원 인가 | XMODEM |

SoC는 OSPI·QSPI·SPI·xSPI·Ethernet·I2C·eMMC·GPMC도 지원하지만 보드에 해당 부품이 없다.
SRM 3.6.1은 eMMC를 풋프린트만 있고 실리지 않았다고 적는다. 이더넷 PHY와 부트용 플래시도
실리지 않았다. USB 호스트 MSC는 포트가 있어 부품 문제는 아니다.

여기서 실용적으로 중요한 것은 두 번째 줄이다. SD 카드를 뽑으면 자동으로 USB DFU로
넘어온다. SD 카드 내용을 건드리지 않고 부트로더를 시험할 수 있다는 뜻이고, 이 문서에서
계속 쓰는 방법이다. 자세한 것은 [05. DFU로 부팅시키기](05-dfu.md)에서 다룬다.

스트랩이 primary를 MMC로, backup을 DFU로 지정하고 USB 호스트 MSC를 고르지 않는다는 것은
SRM 서술과 관측된 동작에서 얻은 추론이다. `0x43000030`을 직접 읽어 확정한 값은 아니다.

## 2-7. 어디까지 우리가 바꿀 수 있나

부팅 과정을 알았으면 다음 질문은 "그중 어디를 내 코드로 바꿀 수 있나"이다.

```
     저항·USER 버튼        하드웨어 변경으로만
     마스크 ROM            대체 불가
------------------------------------------------ 실리콘에 고정
     SMS의 TIFS·HSM 펌웨어  TI 바이너리
     tifsstub-*, dm-tifs   ti-linux-firmware의 TI 바이너리
------------------------------------------------ TI 영역
     tiboot3.bin           R5 SPL, R5 DT
     tispl.bin             TF-A, OP-TEE, DM, A53 SPL
     u-boot.img
     커널·유저스페이스
------------------------------------------------ 소스 빌드 가능
```

직접 만든 코드로 채울 수 있는 최상단은 `tiboot3.bin` 안의 R5 SPL이다. 그 위는 TI가
서명해 배포하는 바이너리이거나 실리콘에 고정된 것이라 손댈 수 없다.

이 경계를 아는 것이 실전에서 중요하다. 부팅이 안 될 때 "내 코드가 도달하기 전에
멈췄다"와 "내 코드가 돌다가 멈췄다"를 가르는 기준이 되기 때문이다. 콘솔에 SPL 배너가
찍혔다면 이미 우리 코드까지 온 것이다.

## 정리

- 단계가 여럿인 이유는 DRAM을 켜기 전에 실행할 곳이 SRAM뿐이기 때문이다.
- ROM이 부팅 장치를 정하고, SPL은 그 결과를 읽기만 한다.
- SD 카드를 뽑으면 USB DFU로 넘어온다. 이게 안전한 실험 경로다.
- 우리가 만들 수 있는 최상단은 R5 SPL이다.
